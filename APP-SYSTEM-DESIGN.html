LC Coach Companion — System Design MVP

A small, local CLI that handles the second half of the LC Coach Kit loop — habit-aware code review + session logging — fully automated, nothing else to wire up. Implemented as lc.py in this repo (~400 lines, one dependency).

Scope discipline (read first): this is a contained weekend build, not a platform. Ship a small MVP, time-boxed, then stop. The non-goals below are load-bearing.

1 · Purpose

ProblemThis tool
Hand-maintaining the logs and getting a code-specific second opinion is manualOne tiny local CLI automates both, scoped to only your LC files
The voice coach (Claude app) can't write to local log filesThis can — append to the queue, tick the tracker, add a weak-area tag
You want a clean, shippable artifact in the agentic / LLM-dev-tooling laneThis is one: a scoped local agent that reviews code against tracked context and writes structured logs

2 · Scope & Non-Goals

In scope (MVP):

  • Local Python CLI, bring-your-own ANTHROPIC_API_KEY
  • Operates on a single configured folder (a clone of lc-coach-kit)
  • Three commands: review, log, status

Explicit non-goals — do NOT build in MVP:

  • ✗ Hosting / multi-user / accounts / auth
  • ✗ A database (the markdown files are the store)
  • ✗ A web UI or desktop app (CLI only — web wrapper is a maybe-v2)
  • ✗ Doing the voice coaching (that stays in the Claude app)
  • ✗ Touching any file outside the configured LC folder

5 · Commands (UX)

# one-time SETUP — pick your language(s) + name
lc setup
   # prompts: name (optional) · primary language · optional 2nd (diagnostic) language
   # writes config the other commands read; tailors the standards gate + review

# ARM the voice coach with a problem → outputs a "session pack" to upload
lc arm "11 Container With Most Water"
   --mode INTERVIEW           # coach delivers it verbally; you stay blind
   # session pack = coaching brief + the problem statement
   #   + your prior attempts on it + your flagged weak-spots
   # upload THAT to the Claude voice session (not the bare brief)

# TIMER — auto-started by `arm`, auto-stopped by `log` (explicit control if needed)
lc start                      # start the session timer (start time + problem)
lc stop                       # stop → elapsed feeds "time vs 50-min cap"

# paste code; prints a habit-aware review (uses weak-areas.md)
lc review
   --problem "1 Two Sum"      # optional, sharpens the review
   --file solution.cpp        # alternative to pasting

# paste your session report; updates the log files
lc log                        # → appends spaced-rep-queue, ticks tracker,
                              #   updates weak-areas tag, appends habits row

# prints spaced-rep items due today/overdue + flagged weak areas
lc status

# GAP ANALYSIS — review accumulated logs, find trends, prescribe next focus
lc gap
   # reads weak-areas + spaced-rep history + habits across sessions
   # prints aggregate gaps (3+ repeats, trending-wrong) + next-week adjustment
   # appends to gap-analysis-log.md

Input by paste (stdin, Ctrl-D to end) or --file. Output to terminal; log also writes files and prints a diff of what changed.

Arming the coach — the feature that makes INTERVIEW mode work. The voice coach needs the problem statement to deliver it verbally while you stay blind — the bare brief can't do that. lc arm "<problem>" builds a session pack = the coaching brief + the problem statement + your prior attempts on this exact problem + your flagged weak-spots. You upload the pack (not the generic brief), so the coach is now problem-aware and history-aware: it can read the problem to you aloud for the INTERVIEW protocol, and it already knows you failed this one on attempt 3 with a dedup bug and watches for it. Two problem sources, both clean: the coach can assume the problem itself (recall or pose one by name/pattern — great for quick, varied practice, though it may paraphrase from memory), or you paste the exact problem (recommended — full fidelity, no hallucination). No scraping, no bundled bank required. The tool supports both.
Setup — language pair + name. lc setup captures your name (optional, for personalization) and your language — or a language pair: a primary (what you code in) + an optional diagnostic second language. The pair powers the cross-syntax check: if your algorithm transfers cleanly to the second language (e.g. Python), the gap was language-structural, not conceptual — so you drill the syntax, not the algorithm. Setup writes a small config that tailors the standards gate (the includes/idioms to watch) and the review to your language.
Gap analysis — the aggregate review. Per-session tagging (in weak-areas.md) catches single mistakes; lc gap steps back and reads across sessions — spaced-rep history + weak-area tags + habits — to surface trends: what's repeating 3+ times, what's trending the wrong way, and the one focus to add next week. It appends a dated entry to gap-analysis-log.md. Run it weekly (the "Sunday review").
Session timing — automatic. The CLI times your solve natively off the system clock — no hook needed (a time-injection hook only matters for giving a conversational AI time-awareness; a CLI process reads the clock directly). lc arm auto-starts the timer, lc log auto-stops it, and the elapsed drops into the report's "time vs 50-min cap" — measured, not eyeballed. Explicit lc start/lc stop are there if you want to pause or control it.
No embedded problem bank. The kit ships the problem list (titles/numbers in problem-tracker.md) but not the problem statements — those are LeetCode's copyrighted content and can't be bundled or scraped. when you want a specific problem, arm takes the text you provide: paste it at arm-time, or keep your own personal problems/<id>.md files (your copy, for your use — never committed to the public repo). The problems/ folder ships empty, a convention you fill yourself. (Or just let the coach pose one itself — see above.)

The two modes in voice — TEACH vs INTERVIEW

The CLI touchpoints are identical; what changes is how the voice coach behaves. You set it with lc arm "<problem>" --mode TEACH|INTERVIEW.

TEACH — learning or stuck. Warm-up quiz first (curated from your tracked gaps), problem shown, Socratic nudges toward the insight:

Coach: Quick warm-up before we read it — from your tracked gaps: on a two-pointer dedup, where does the skip-duplicates step go?
You: After recording the result, advance past equal neighbors on both pointers.
Coach: Good. And generally, N² + N log N dominates to…?
You: O(N²).
Coach: Right. Problem: two-sum on a sorted array. State the job in plain English first.
You: Find two numbers that add to target… I'll use a hash map?
Coach: You could — but it's sorted. Does that unlock something simpler?
You: …two pointers from both ends.
Coach: There it is. Why move the left pointer when the sum's too small? (you reason it out — coach only nudges, never tells)

INTERVIEW — you know it, performing. Verbal delivery, restate cap, you stay blind, coach goes quiet:

Coach: [reads the problem aloud once] You can ask me to restate it twice.
You: Restate the constraints? (1 of 2 used)
Coach: [restates]
You: [invents an example, traces it, writes pseudocode aloud]
Coach: (silent — lets you work)
You: Complexity is O(N)?
Coach: Are you sure that handles all-duplicates? (probes — doesn't fix)

6 · Data Flow

review — read-only

code + weak-areas.md  ──►  Claude  ──►  review text  ──►  printed to user

Nothing is written. The weak-areas context is what makes it habit-aware — it flags the mistakes this user actually repeats.

log — read + write

session report + current log files  ──►  Claude (structured extraction)
      ──►  proposed updates (queue row, tracker tick, weak-area tag, habit row)
      ──►  file store appends/edits  ──►  prints what changed
Diff before write. Claude extracts structure from the free-text report; the file store applies deterministic appends. Show the before/after so a mis-parsed report can't silently corrupt the logs.

7 · Data Model

No database — the markdown files are the store:

  • weak-areas.md — tag table (read for review context; appended on log)
  • spaced-rep-queue.md — active queue (appended/updated on log; read for status)
  • problem-tracker.md — checkboxes (ticked on a clean solve)
  • habits.md — daily rows (appended on log)
  • config.md — name + language(s) from setup (read by all commands)
  • gap-analysis-log.md — dated aggregate-review entries (appended by gap)
  • problems/<id>.md — optional cached problem statements (read by arm)
  • .session — timer state (start time + current problem; set by start/arm, cleared by stop/log)

8 · Tech Stack

  • Python 3.10+, stdlib + the anthropic SDK. That's it.
  • No web framework, no DB, no async. One package dependency.
  • Config via env vars (ANTHROPIC_API_KEY, optional LC_DIR).

11 · Guardrails

  • Path-scoped: the file store rejects any write outside the configured LC folder. Never touches the rest of the machine.
  • Diff-before-write: log shows the change (and can confirm) before saving — a mis-parsed report can't corrupt the logs.
  • Read-only review: review never writes.
  • BYO key: no shared credentials, no hosting cost on you.

11b · Safety & Trust — is it safe to run?

A fair question for any AI tool with file access + network calls. Why you can trust it:

  • It's open source. ~390 lines you can read end to end — no hidden behavior, no obfuscation.
  • The AI never executes anything. It only returns text (a review, or structured log data). The tool's own deterministic code does the file writes — no eval, no running the model's output as code or shell commands.
  • File access is hard-scoped. The file store refuses any path outside your LC folder. It cannot read or write the rest of your machine.
  • Read-only review. review never writes — it only prints.
  • You approve every write. log shows a diff of the proposed change (and can confirm) before saving — a bad parse can't silently corrupt your logs.
  • You control what leaves your machine. Only the code/report you paste + the kit files (sent as context) go to the Anthropic API, under your own key. No telemetry, no other network calls, no third-party servers.
In short: a small, readable, local tool that talks to exactly one API (with your key), writes only inside one folder, and never runs AI output as code. You can verify every line.
